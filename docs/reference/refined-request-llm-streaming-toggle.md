# Refined Request: Optional Configurable LLM Response Streaming

## Category
Development

## Objective
Make the existing one-shot blocking LLM refinement/translation pipeline able to stream the LLM **response tokens** (Azure OpenAI SSE via `"stream": true`; Google Gemini via `:streamGenerateContent?alt=sse`), read them incrementally, and render the refined/translated text progressively in the overlay's `finalizing` phase — and expose this entire behavior as an **optional, user-toggleable feature** that is **off by default** (preserving today's one-shot behavior) and integrates with the project's existing four-tier configuration system (shell env → `~/.tool-agents/untype/.env` → local `.env` → CLI flags) and UI settings. The atomic insertion of the final text into the focused input control and all push-to-talk wiring must remain unchanged and unregressed.

## Scope
- **In scope**
  - A new on/off configuration flag (CLI flag + `UNTYPE_*` env var + UI settings toggle) that enables/disables LLM response-token streaming. Default: **off** (current one-shot behavior).
  - Streaming the LLM **response** for BOTH currently implemented providers: `AzureOpenAIRefiner` (Azure OpenAI Chat Completions SSE) and `GoogleRefiner` (Gemini `streamGenerateContent` SSE).
  - Incremental reading of the response stream (e.g. `URLSession.bytes(for:)` / `AsyncBytes`, parsing SSE `data:` frames and accumulating deltas) behind the existing `LLMHTTPClient` / `TextRefining` abstractions, without breaking the non-streaming path.
  - The single-shot `.refine` operator path (`refiner.refine()`) streaming its output progressively.
  - The standalone `.translate` operator path (`translator.refine()` with the rendered translation prompt) streaming its output progressively.
  - The composite refine+translate path (`LLMCompositeRefineTranslator.refineAndTranslate()`), which asks the model for a single JSON object `{refined_text, translated_text}` — define and implement what "streaming" means for it (see Requirement 6).
  - Progressive rendering of streamed text in the overlay `finalizing` phase (`NativeUntypeUILauncher.stopHotkeySession` / `overlay?.show(phase: "finalizing", …)`), updating displayed text as tokens arrive instead of showing only the raw transcript.
  - Wiring the flag through `ConfigResolver` → `ResolvedConfig`/`LLMConfig` → refiner construction (`LLMRefinerFactory`) and through `UntypeUISettings` / `UntypeUISettingsPatch` for the UI toggle, including the setting-source reporting consistent with existing flags.
  - Updating `docs/design/project-design.md`, `docs/design/project-functions.md`, and (if config docs exist) a configuration-guide entry for the new flag.
- **Out of scope**
  - **Pre-release streaming ("Dimension B")**: refining/translating a partial transcript before the push-to-talk key is released. Explicitly excluded as out-of-scope and semantically wrong for translation.
  - Changing focused-input delivery to incremental/append insertion. Insertion into the focused input control stays **atomic on stream completion** (project guardrail — must not regress).
  - Implementing streaming for providers not currently implemented (`openai`, `anthropic`, `azure-ai-inference`, `ollama`, `litellm`, `openai-compat`); they remain `.unimplemented`.
  - Changing the STT (speech-to-text) streaming path, which already streams.
  - Changing the LLM provider set, prompts, or refine/translate semantics beyond what streaming requires.

## Requirements
1. **On/off configuration flag.** Introduce a single boolean setting (working name `llmStreaming`) that enables LLM response-token streaming. It MUST be resolvable via: a CLI flag (e.g. `--llm-streaming` / `--no-llm-streaming` switch pair, matching the `--refine`/`--no-refine` and `--quick-close`/`--no-quick-close` precedents) and an env var (e.g. `UNTYPE_LLM_STREAMING`) parsed with the existing `parseBoolean` accepted token set (`true,false,yes,no,on,off,1,0`). Precedence MUST follow the established chain (CLI flag highest, then local `.env`, then `~/.tool-agents/untype/.env`, then shell env), consistent with how other booleans resolve in `ConfigResolver`.
2. **Default = off.** When the flag is not provided at any layer, streaming is disabled and behavior is byte-for-byte equivalent to today's one-shot path. This documented default is a deliberate optional-toggle default and does NOT violate the "no silent fallback for required config" rule (the toggle is optional, not required). The default and its rationale MUST be documented.
3. **Config-rule compliance.** No new *required* configuration value is introduced; therefore no new "missing config must raise" case is created by this feature. If any sub-setting were ever made required, it must raise rather than fall back (per project rule) — but the streaming toggle itself is optional with a documented default.
4. **Azure OpenAI streaming.** When streaming is enabled and provider is `azure-openai`, the request MUST set `"stream": true`, the client MUST read the SSE response incrementally, parse `choices[].delta.content` fragments, accumulate them, surface incremental text to a progress callback, and return the same fully-accumulated, trimmed string the one-shot path returns. Error/`shape`/`auth`/`server`/`timeout` classification (`LLMRefinementError`) and HTTP status validation MUST be preserved for the streaming path.
5. **Google Gemini streaming.** When streaming is enabled and provider is `google`, the request MUST target `:streamGenerateContent?alt=sse`, read the SSE response incrementally, parse `candidates[].content.parts[].text` fragments, accumulate them, surface incremental text to a progress callback, and return the same fully-accumulated, trimmed string the one-shot path returns, with equivalent error classification.
6. **Composite refine+translate streaming semantics.** The composite path returns one JSON object `{refined_text, translated_text}`. The implementation MUST define streaming for it explicitly. Required behavior: stream the underlying model response tokens so the overlay can show live progress (e.g. raw accumulated JSON-in-progress or a best-effort partial extraction), BUT the structured `CompositeRefineTranslateResult` (and the `refined_text`/`translated_text` fields delivered downstream) MUST be parsed only from the **complete** accumulated response — partial JSON must NOT be parsed into final fields and must NOT be inserted into the focused input. The progressive overlay display for the composite path may show provisional/partial text and MUST be clearly non-final until completion. The exact partial-display strategy is an Open Question with a recommended default below.
7. **Progressive overlay rendering.** During the `finalizing` phase, the overlay MUST update its displayed text as streamed tokens arrive (replacing today's behavior of showing the raw transcript only), and MUST settle on the final refined/translated text when the stream completes. This rendering MUST be driven by the streaming progress callback and MUST be a no-op (identical to current behavior) when streaming is disabled.
8. **Atomic focused-input delivery preserved.** Insertion into the focused input control MUST happen exactly once, atomically, only after the stream completes and the full final string is available (`FocusedInputDelivery` unchanged in behavior). No partial/streamed text is ever inserted into the focused input or clipboard. The newest `~/.tool-agents/untype/release-latency.jsonl` record after a streamed release into a focused field MUST show `focused_input.ok=true`.
9. **Push-to-talk wiring preserved.** Hotkey listening, press/release routing to the runtime session, audio-gate open-on-press/close-on-release, and overlay recording/finalizing show/hide behavior MUST remain fully functional (`NativeUntypeUILauncher`, `UntypeHotkeyMonitor`, `HotkeySessionControl`, `TranscriptionSessionRuntime`).
10. **Abstraction integrity.** Streaming MUST be introduced behind the existing protocols (`LLMHTTPClient`, `TextRefining`, `CompositeRefineTranslating`) via additive, optional streaming entry points (e.g. a streaming variant method or a progress-callback parameter) so the non-streaming path and existing call sites/tests remain valid. Existing one-shot `perform`/`refine` signatures should remain usable when streaming is off.
11. **Diagnostics & latency parity.** Existing operator diagnostics (`operatorDiagnostic(.refine/.translate, stage:)`), failure logging (`logOperatorFailure`), and `summary.refineMs`/`translateMs` timing MUST continue to be produced for the streaming path (timing measured to stream completion).
12. **UI settings integration.** `UntypeUISettings` (and `UntypeUISettingsPatch`, the settings UI, and `UntypeUISettings.default`) MUST gain the streaming toggle with a sensible label, defaulting to off, persisted and reflected like other operator/config toggles.
13. **Documentation.** Update `docs/design/project-functions.md` (new functional capability), `docs/design/project-design.md` (design decision + provenance chain references), and the configuration guide (if present) with the new flag's purpose, options, precedence, and default.

## Constraints
- **Language/platform:** Swift, macOS app (`UntypeCore`). Build via `swift build`; run focused hotkey/push-to-talk tests where available; manual smoke check where macOS permission/overlay behavior cannot be automated.
- **Networking:** Reuse the process-wide shared `URLSession` keep-alive strategy (`URLSessionLLMHTTPClient.sharedSession`); streaming reads MUST not break connection reuse, cancellation (`cancelAll`/`activeTasks`), or the privacy posture (no cache/cookies).
- **No silent config fallbacks** for *required* settings (project rule); the optional streaming toggle's documented default is permitted.
- **Guardrails:** Do not break push-to-talk; do not break focused-input delivery (both are fundamental, non-regressable features).
- **Config plumbing pattern:** Follow the existing `ConfigResolver` switch/flag patterns, `ParsedArguments` flag registration (add the new flag(s) to the recognized option lists), and `ProtocolSettingSources`/`configuredSource` reporting style if surfacing setting source.
- **Tooling:** Any new test scripts go under `test_scripts/`. No version-control operations unless explicitly requested.

## Acceptance Criteria
1. With no streaming flag/env/UI toggle set, end-to-end behavior (refine, translate, composite, overlay, focused-input insertion) is functionally identical to the pre-change one-shot behavior; existing tests pass unchanged.
2. Setting `--llm-streaming` (or `UNTYPE_LLM_STREAMING=on`, or enabling the UI toggle) enables streaming; precedence is verifiably CLI flag > local `.env` > `~/.tool-agents/untype/.env` > shell env, with a test asserting the resolved value at each layer.
3. With streaming on and provider `azure-openai`, an Azure refine/translate request is sent with `"stream": true`, the SSE response is consumed incrementally, and the returned final string equals what the one-shot path would have produced for the same input (verified with a mock/stub SSE client).
4. With streaming on and provider `google`, the request targets `:streamGenerateContent?alt=sse`, the SSE stream is consumed incrementally, and the returned final string equals the one-shot equivalent (verified with a mock/stub SSE client).
5. With streaming on, the composite refine+translate path streams tokens for overlay progress, but `CompositeRefineTranslateResult.refinedText`/`translatedText` are parsed only from the complete response; partial JSON is never parsed into final fields nor inserted anywhere (verified by a test feeding a partial-then-complete SSE sequence).
6. During a streamed release, the overlay `finalizing` phase visibly updates displayed text as tokens arrive and settles on the final text on completion (manual/automated overlay check); with streaming off, the overlay behaves exactly as today.
7. Focused-input insertion occurs exactly once, atomically, after stream completion; the newest `release-latency.jsonl` record shows `focused_input.ok=true` after a streamed release into a focused text field.
8. Push-to-talk press/release, audio gating, and recording/finalizing overlay transitions work with streaming both on and off (manual smoke check + any available hotkey tests).
9. Error classification (`auth`/`network`/`timeout`/`server`/`shape`), HTTP status validation, operator diagnostics, failure logging, and `refineMs`/`translateMs` timing are produced for the streaming path equivalently to the one-shot path (unit tests for error/shape cases on streamed responses).
10. `swift build` succeeds; `docs/design/project-functions.md`, `docs/design/project-design.md`, and the configuration guide (if present) are updated to describe the new flag (purpose, options, precedence, default = off).

## Assumptions
- **[Flag naming]** The CLI flag is `--llm-streaming` / `--no-llm-streaming` and the env var is `UNTYPE_LLM_STREAMING`, mirroring existing `--refine`/`--no-refine` + `UNTYPE_REFINE` conventions. Basis: consistency with the codebase's established flag-pair and env-naming patterns.
- **[Default off]** Streaming defaults to OFF to preserve current behavior unless the user opts in. Basis: the raw request says "defaulting to the current one-shot behavior unless specified," and one-shot is today's behavior.
- **[Scope = response streaming only]** Only LLM *response-token* streaming (Dimension A) is implemented; pre-release/partial-transcript streaming (Dimension B) is excluded. Basis: explicit instruction in the request context.
- **[Atomic insertion retained]** Focused-input insertion and clipboard delivery remain atomic on completion; streaming affects only overlay display, not delivery. Basis: project guardrail that focused-input delivery is fundamental and must not regress.
- **[Additive abstraction]** Streaming is added as an additive, optional capability on `LLMHTTPClient`/`TextRefining`/`CompositeRefineTranslating` (e.g. an optional progress callback or a parallel streaming method), keeping existing signatures and call sites valid. Basis: minimizing regression surface and preserving existing tests.
- **[Setting threading]** The streaming flag is threaded through `LLMConfig` (new field) into `LLMRefinerFactory.make*` so each refiner knows whether to stream. Basis: refiners are constructed from `LLMConfig`; this is the least-invasive injection point.
- **[Project docs exist]** `docs/design/project-design.md` and `docs/design/project-functions.md` exist and must be updated; a configuration-guide update applies only if `docs/design/configuration-guide.md` exists.

## Open Questions
- **Question:** What exactly should the overlay show for the **composite** path while streaming, given the response is in-progress JSON?
  - **Why it matters:** Determines UX during composite refine+translate and how much partial-parsing logic is needed; affects the progress-rendering design and tests.
  - **Recommended default:** Show a best-effort live extraction of the streamed `refined_text`/`translated_text` values as they accumulate (incremental string-scan of the partial JSON, displayed as clearly non-final), and fall back to showing raw accumulated text if partial extraction is not yet possible — never parsing partial JSON into the final structured result.
- **Question:** Should a UI settings toggle be required for v1, or is CLI/env sufficient initially?
  - **Why it matters:** Adds work in `UntypeUISettings`/`UntypeUISettingsPatch` and the settings UI; affects scope/timeline.
  - **Recommended default:** Include the UI toggle in v1 (full parity with other operator/config toggles) since the request frames this as a user-facing optional feature the user can "turn on or off."
- **Question:** For non-streaming-capable / unimplemented providers, what happens if the streaming flag is on?
  - **Why it matters:** Avoids surprising behavior when streaming is enabled but the active provider can't stream.
  - **Recommended default:** Streaming applies only to `azure-openai` and `google`; for any other (currently `.unimplemented`) provider the flag is silently inert (no effect, no error) since those providers already error at construction when enabled. Document this clearly.
- **Question:** Should streaming progress also be emitted to the agent-protocol output / diagnostics stream, or only to the native overlay?
  - **Why it matters:** Affects `agentProtocol` mode and event logging surface.
  - **Recommended default:** Drive only the native overlay's `finalizing` display from streaming progress in v1; leave protocol-output and diagnostics on their existing completion-time events to avoid changing the protocol contract.

## Open Questions — Resolutions (resolved by user at orchestrator gate, 2026-06-20)
1. **Composite-path overlay during in-progress JSON** → **Best-effort live extract.** Progressively extract `refined_text`/`translated_text` from the partial JSON for DISPLAY ONLY (shown as clearly non-final); the final committed result must come from fully-parsed JSON, never from partial parsing. (Matches the refiner's recommended default.)
2. **UI toggle in v1** → **Yes — full UI parity.** Add a native settings toggle alongside the other toggles, in addition to the CLI flag and env var. (Matches default.)
3. **Streaming flag on with a non-streaming provider** → **Silently inert.** Streaming applies only to `azure-openai` and `google`; for any other provider the flag has no effect and produces no error/warning. (Matches default.) Note: this is NOT a violation of the project's no-silent-fallback rule — both the streaming flag and the provider are present/valid; the optional feature simply has no effect for providers that cannot stream. No missing-config substitution occurs.
4. **Progress channels** → **Also emit to agent-protocol/diagnostics** (CHANGED from the refiner's default of overlay-only). In addition to driving the native overlay `finalizing` display, emit incremental streaming progress events to the agent-protocol JSONL output and verbose diagnostics stream. This expands the surface vs. the recommended default — the design and tests must cover the protocol/diagnostics streaming events as well, while keeping the existing completion-time `sectionProcessed` event intact for backward compatibility.
